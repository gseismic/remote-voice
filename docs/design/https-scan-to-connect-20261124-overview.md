# HTTPS 中继与扫码直连

## 用户操作

Mac 的连接设置接受 `https://voice.gpt60.com`。设置服务器密码并连上中继后，点击「二维码」。Android 从「＋ 添加 → 扫码配对」读取连接信息，自动连接二维码对应的 Mac。「已就绪」沿用现有主屏状态，用户此时可按住说话测试。首次使用需要 Android 授予麦克风权限。中继认证成功和建桥成功是两个状态，Mac 离线或正在被使用时显示现有错误原因。

已有配置可继续手动选 Mac。旧二维码缺少设备 ID 时仍能用于添加中继和选择 Mac。新二维码按设备 ID 连接，同名和改名不会改变目标。

## 入口方案

| 方案 | 适用条件与代价 |
| --- | --- |
| 原生 TLS 在独立端口加公有证书 | 两端无需新传输层。依赖云端额外放行，域名无法作为标准 HTTPS 网址使用。 |
| 公网 HTTPS 下使用 WebSocket | 使用浏览器可用的传输。三端均需引入 WebSocket 编解码与流适配。 |
| 公网 HTTPS 下使用 HTTP/1.1 Upgrade | 复用 Nginx 现有 443 和原生客户端的字节流。升级后直接传输 v4 帧，三端继续使用既有标准库与依赖。适合本项目的原生客户端。 |

采用第三种方案。Mac 端 `https://host[:port]` 缺省走 443，对证书链及主机名做标准验证。HTTP/1.1 `GET /relay` 申请 `Upgrade: remote-voice`。收到 `101` 和匹配的升级头后发送 v4 AUTH。Nginx 转发到仅监听回环的 Go HTTP 入口，提供 `GET /healthz`。浏览器访问域名根路径可确认 HTTPS 已可用。HTTP 80 提供证书验证并重定向普通请求。参考 [Nginx 升级转发](https://nginx.org/en/docs/http/websocket.html) 与 [Let's Encrypt HTTP-01](https://letsencrypt.org/docs/challenge-types/#http-01-challenge)。

## 配对与授权

- HTTPS 配对码采用 `rvh://host[:port]?s=<密码>&d=<设备ID>&n=<名称>`。自定义 URI 避免扫码器将密码当作浏览器网址的一部分提交。`s` 必填，`d` 和 `n` 可选。原生 TLS 地址保留显式信任模式，默认端口仍为 9432。
- Android 同一次配置写入保存地址、密码、信任模式和扫码目标，显式配对可以恢复手动停用的服务。连接、手动切换和断开复用现有桥接操作，恢复目标与目录缓存按服务器隔离。
- HTTPS 中继只认证已登记的 Mac。当前生产 Mac 从已存在的局域网登记迁移设备身份摘要。管理员可通过 SSH 转发的本机原生 TLS 入口登记其他 Mac。手机沿用服务器密码认证，Nginx 覆盖来源 IP，供中继保持按 IP 限速。

## 复核

- 证书或 HTTP 升级失败时，两端在发送 v4 凭据前停止该次连接。Nginx 无需读取 v4 数据或密码，线上只有专属虚拟主机终止 TLS。
- 同一服务器进程同时处理两条入口，目录与桥共用同一份设备状态。服务端升级读取缓存和客户端响应读取缓存都随连接保留，后续帧可紧跟升级响应。Android 已存的服务器条目缺少模式字段时仍按原有自动模式读取。
