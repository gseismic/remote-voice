# PLAN-011：Android 手机无法连接修复

日期：2026-08-28
基线提交：`d029e7da977ec246c8b00e6f1fe41dd4a8ee24d3`
关联计划：[PLAN-010-tauri-mac-client.md](PLAN-010-tauri-mac-client.md)

## 1. 用户目标

用户反馈：Mac Tauri 可以连接 server，但 Android 手机无法连接或看起来没有反应。
本次目标是让 Android 在添加 Mac 配对秘密后确实进入连接流程，并在连接失败时保留可读错误，便于区分网络、TLS、秘密认证和麦克风权限问题。

## 2. 侦查结论

1. `android-app/app/src/main/java/com/remotevoice/app/MainActivity.kt` 的主页面“添加设备”回调只调用 `store.add()` 和 `renderDevices()`，没有调用 `maybeAutoStart()`；首次从主页面添加设备不会自动启动前台连接服务。
2. `android-app/app/src/main/java/com/remotevoice/app/AudioStreamService.kt` 的 `onFatal()` 和启动前校验会写入错误状态，但 `onDestroy()` 无条件把状态改成 `STOPPED/未启动`，导致 AUTH_ERR、服务器地址错误和音频初始化错误无法在主界面留存。
3. `AudioStreamService.stopStreaming()` 只关闭客户端并丢弃线程引用，没有中断/等待 relay 线程；快速切换设备或服务重启时，旧线程可能晚到回调并覆盖新状态。
4. v3 线路本身保持一致：Android 发送 `role=phone、proto=3、secret=SHA-256(规范化秘密)`；Mac Tauri 发送 v3 身份并 REGISTER 配对秘密，server 的路由顺序无需修改。
5. 设置页的“添加设备”仍不会让正在运行的服务切换到新设备；主界面原有的固定 600ms 延迟也无法保证旧服务已经退出。
6. `AudioStreamService` 用字符串截取解析服务器地址，只接受裸 `host:port`；用户直接粘贴 server 打印的 `rv://...` 地址时会把主机解析错。
7. Android 13+ 当前把 `POST_NOTIFICATIONS` 和录音权限捆绑为“全部授予才启动”；通知权限不是连接/采音的前置条件，拒绝它会造成手机端看似没有反应。

## 3. 实施步骤

1. 主页面与设置页添加/切换设备后清除手动停止标记并触发权限检查/自动连接。
2. 在 Android 服务内提供串行重启动作，统一错误退出路径，保留错误状态直到用户主动重试；正常停止仍显示“已停止”。
3. 停止服务时关闭阻塞中的 TCP 连接、打断并有限等待 relay 线程，避免旧线程回调污染新连接。
4. 统一解析裸 `host:port` 与 `rv://host:port`，并只把录音权限作为启动前置条件。
5. 增加连接代次与采音代次校验，隔离已排队的旧连接回调；删除当前设备时切换剩余设备或停止服务。
6. 运行 Android 构建，并复核 Kotlin 改动、协议字段和工作树差异。
7. 生成对应结果文档，更新 `docs/dev/INDEX.md`、`docs/HANDOFF.md`，中文提交并推送。

## 4. 验收标准

- 从主页面新增 Mac 秘密后自动触发连接，不需要额外点击状态条。
- 从设置页新增/修改设备或服务器后，正在运行的连接切换到最新配置，不依赖固定等待时间。
- AUTH_ERR、网络失败、服务器地址错误和 AudioRecord 初始化失败在主界面/通知中保留可读错误。
- `rv://服务器IP:端口` 和 `服务器IP:端口` 两种地址输入都能得到相同连接目标。
- Android 13+ 即使拒绝通知权限，只要录音权限已授予，仍能启动前台采音连接。
- 用户主动停止或正常销毁服务时仍进入停止状态；服务重启不会被旧 relay 线程的回调覆盖。
- `./gradlew assembleDebug` 通过；Mac/Tauri、server 和协议文件无无关修改。
- 设备切换/删除后，旧网络或采音线程不能改变新连接状态，也不能向新连接发送音频。
- 真实 Android 设备验证仍需用户侧执行，自动化环境没有连接的实体设备。

## 5. 计划自查

### 第 1 遍：范围

- 只修复 Android 连接触发、配置解析、错误可见性和线程生命周期，不改变 v3 协议或认证安全边界。

### 第 2 遍：状态

- 错误状态必须与正常用户停止区分；重试时显式清除旧错误。
- 服务销毁不能在 relay 线程仍运行时启动第二个有效连接；阻塞中的 TCP 拨号也必须可被停止动作打断。
- 通知权限属于可选可见性能力，不能阻断录音连接。

### 第 3 遍：验证

- 构建验证只能证明 Kotlin 编译；结果文档必须明确没有实体 Android 运行验证。

## 6. 实施后复核追加

- 复核发现旧采音线程不能重新读取共享 `client`，已改为绑定创建时的 relay 实例。
- 复核发现切换设备时误清理主页面状态轮询，已移除该清理副作用。
- 复核发现错误停服后重新添加正确秘密需要显式清除旧错误，已统一由用户主动重试、添加或保存设置触发。
- 最终状态机修正完成：主页面状态轮询持续运行，设置页修改当前设备会清除错误并触发后续连接。
- 继续复核发现 relay 瞬断自动重连时旧采音线程未收到掉线通知，需补充断线事件与连接会话隔离。
- 最终完成断线隔离：relay 每次底层连接结束都通知掉线，采音代次在释放前递增，旧线程不能跨自动重连发送音频。
- 运行时复核补充前台麦克风服务启动异常的可见错误，并将当前设计文档改为明确拒绝旧 `?f=` 参数。
- 继续复核发现服务重启没有等待旧采音线程退出，需在关闭旧 relay 后有限等待旧录音线程，避免新连接抢占麦克风。
- 最终完成重启资源顺序修正：先使旧代次失效、关闭旧 relay、释放 `AudioRecord`，再有限等待旧采音和网络线程。
- 交接记录同步为 Android 仅支持当前 v3 输入流程，未把旧 `regkey`/指纹配置兼容描述为现行能力。
- 复核发现旧采音线程异常可能误杀新连接，已加入代次、relay 实例和 `AudioRecord` 三重校验；前台服务运行时启动异常统一转为可见错误。
- 设置页删除当前设备且服务已停止时自动返回主页面，由主页面继续触发剩余设备的自动连接。
