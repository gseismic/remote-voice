# PLAN-037 Android 公网连接真机验收

- 基线 `9ec0217`
- 编写于 2026-11-24（Asia/Shanghai）
- 用户希望定位新版 Android 点按连不上的原因，完成修复并自行验收。验收覆盖公网中继、实体手机、目标 Mac 的按住说话与 Fn 联动。

## 排查与验收计划

1. 核对手机的已安装 APK、当前中继地址、连接状态和日志。保留手机配对数据，优先复现现有故障。对照公网 HTTPS 升级、手机登录、目录和桥接日志确定故障环节。
2. 使用实际发布 APK 检查点选 Mac、扫码直连、Mac 晚启动后自动恢复以及关闭自动重连后的手动恢复。区分实体手机和模拟器的证据。
3. 在目标 Mac 只观察 Fn 修饰键状态。用 Android 按下和松开，核对 TALK、音频、桌面 Fn 状态和中继日志的时间对应。
4. 按复现结果更新本计划并实施修复。构建和覆盖安装后复测，复审没有后续代码修改的一轮，再记录结果。涉及仓库改动时提交并推送，更新 APK 下载入口。

## 实施前复核

1. `/healthz`、设备在线以及模拟器成功各自只覆盖一部分路径。实体手机要在 ADB 状态为 `device` 时实际读到状态，并以该手机建桥结果验收。
2. 设备 USB 描述符读取 `-71` 和 ADB 收发协议错误发生在应用之前。只重新初始化手机对应的 USB 接口，避免影响其它设备。接口不稳定时保留证据并继续独立验证公网和 Mac。
3. 公网实测使用现有配对配置，保护密码。建桥前确认目标 Mac 空闲，测试结束释放测试会话。Fn 样本只记录目标修饰键。

## 联调定位

- 发布 APK 已在模拟器上通过公网 HTTPS 登录，点选目标 Mac 后显示「已就绪」。目标手机的 USB 接口曾完成 ADB 握手，随后因内核 USB 描述符和收发协议错误掉线，仍需取得稳定真机链路。
- 目标 Mac 的 `tccd` 核对到辅助功能登记仍要求旧版 CDHash `e347e3e3…`，当前安装包为 `a2fba748…`。系统应用注册还包含从磁盘映像和构建目录启动的临时副本。清理这些副本的应用注册后，使用系统面板为 `/Applications/Remote Voice.app` 重新保存许可，再复测 Fn。
- Android SDK 的 `api-versions.xml` 显示 `URLDecoder.decode(String, Charset)` 自 API 33 才可用，而 APK 支持 API 26 起。扫码和粘贴共用此路径。实施时改用较早即可用的编码名重载，复核 APK 调用的方法签名与公网配对行为。手机系统版本待在设备上读取。
- Android Lint 也确认该 API 错误及相机权限隐含硬件要求。应用原本支持无相机时粘贴配对码，也可使用非自动对焦相机。将这两种硬件特性显式声明为可选，并复跑 Lint。
