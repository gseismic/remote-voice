## 一、总体结论

**实施质量总体良好，但不能标记为"已完成"。** 发现 2 个高优先级功能缺陷（均已实验复现，
均在 mac-client）、1 个 relay 数据竞争（已用 -race 探针实证）、1 处与计划书的协议级偏差
（`peer-offline` 原因码缺失，且其后果恰是计划 I6 明确要防止的误伤）。测试全绿是真的
（relay -race 20 例、mac-client 14 例、mac-receiver 5 例均复跑通过），但测试面恰好
覆盖不到上述缺陷——回环集成测试全程有帧流动，掩盖了心跳缺失问题。

## 三、发现清单

### H-1 mac-client 无心跳发送方 + 读超时 10s 继承 → 空闲即周期掉线，桥接中静默 >10s 断链
- **证据**:
  - `mac-client/core.py:207-209` `_read_frame_timeout(AUTH_TIMEOUT=10)` 对 socket
    `settimeout(10)`；`core.py:215` `_read_loop` 直接复用该超时，从未恢复为 READ_TIMEOUT。
  - `mac-client/core.py` 全文无任何 PING 发送逻辑（仅 `core.py:218` 回 PONG）；
    对照组：`mac-receiver/receiver.py:55,270-275` 有 10s 心跳线程（v1 遗产，迁移时丢失）；
    `android-app/.../RelayClient.kt:167-177` 也有。relay 侧不主动发 PING
    （`relay/internal/server/session.go:57-85` 只应答），且服务端 40s 读超时兜底前，
    客户端 10s 就先超时。
  - **探针实测**: 正确 regkey 注册成功后空闲观察，+10.2s reconnecting → +11.2s
    registered → +21.2s reconnecting…每 ~10s 掉线一次。
- **影响**: ① Mac 挂机时永远处于"连上→10s→掉线→重连"循环；② 更严重——PTT 场景中
  手机按住说话时音频帧保活，但**松开超过 10 秒后 Mac 侧连接超时断开、桥接解除**
  （relay 不转发手机的 PING，见 session.go:65-66 只在本会话回 PONG）。此后手机即使再按
  PTT 也无法恢复（Android 收到 peer-offline 后不会重新 AUTH，需手动断开重连），对讲
  实际不可用。loopback 测试因全程主动收发帧而未暴露此问题。
- **建议**: 把 receiver.py 的心跳线程移植进 core.py（10s PING + 读超时恢复为 40s），
  并补一条"注册后静默 15s 不断线"的回归测试。

### H-2 指纹不符时 FatalError 从 _attempt 逃逸 → 重连线程死亡，状态永久卡在 CONNECTING
- **证据**: `mac-client/core.py:169` `_verify_pinning(tls)` 位于捕获
  `(OSError, ssl.SSLError)` 的 try 块内，`FatalError`（core.py:205 抛出）不在捕获范围；
  `_run`（core.py:144-156）也无兜底 try。`ST_FATAL` 设计上覆盖"指纹不符"
  （core.py:32 注释），实际只有 AUTH_ERR invalid-key/rate-limited 路径能到达
  （core.py:183-184）。
- **探针实测**: 错误指纹启动 8s 后 `thread_alive=False, state='connecting'`，异常仅打印
  到 stderr。UI 层（ui_main.py:390-402）将永远显示"连接中…"，用户无从得知是指纹错了。
- **建议**: `_attempt` 内单独捕获 `proto.FatalError` 并返回致命标记；补错误指纹用例。

### M-1 relay: authPhone 在锁外读 `reg.name`，与 reapplyRegister 写入构成数据竞争
- **证据**: 写方 `relay/internal/server/server.go:453`（持 mu）；读方 `server.go:336`
  （日志）与 `server.go:340`（AUTH_OK 回传设备名）在 `server.go:332` 解锁之后。
  **-race 探针实测报 DATA RACE**（写 goroutine=reapplyRegister ← readLoop ← handleRegister；
  读 goroutine=authPhone ← handleConn）。现有 20 个用例没有 REGISTER 与手机认证并发的场景，
  故未暴露。字符串头撕裂读在最坏情况下可越界崩溃。
- **建议**: 解锁前把 `reg.name` 快照进局部变量（与 entry.kind 同批读取即可）。

### M-2 计划偏差: `peer-offline` 原因码未实现，Mac 离线坍缩为 `invalid-secret` 且计入防爆破限速
- **计划要求**: PLAN-005 §二.41 枚举含 `peer-offline`；规则 3"Mac 离线=`peer-offline`
  （不计数）"；I6 明确动机"Mac 关机时手机连不上若也算失败，5 次就锁 → 显然误伤"；
  A5 要求用例"Mac 断开后手机 auth 得 peer-offline"。
- **实现**: Mac 断开即删除注册表（server.go:365-374 detach），此后正确秘密的认证走
  "查表 miss → invalid-secret + rate.fail"（server.go:290-297）。
  测试 `TestPhoneAuthWhenMacOfflineRejected`（server_test.go:252-264）把该偏差固化为断言，
  与 A5 的验收描述直接矛盾。
- **后果**: Mac 重启窗口期，手机每次手动点"连接"都累积一次失败计数；60s 内 5 次
  （或多次重启叠加跨级）触发 1m→5m→30m 递增锁定（ratelimit.go:80-93，锁级不复位），
  Mac 恢复后被锁期间即使秘密正确也恒拒（rate-limited）。Android 因 AUTH_ERR 即停
  （RelayClient.kt:84-88 fatal 不自动重试）缓解了自动化误伤，但文案
  "未找到匹配设备（该 Mac 未在线…）"（RelayClient.kt:214）实际是把两个语义粘在一个
  字符串里掩盖了原因码缺失。
- **建议**（三选一，需用户拍板）: a) 补齐 peer-offline——注册表项与 Mac 会话解耦
  （Mac 断开保留哈希、标 offline，重连恢复），离线不计数；b) 维持现状但在
  PLAN/OUTCOME/HANDOFF 显式记档该偏离及理由；c) 至少把"离线导致的 invalid-secret"
  排除出限速计数（无法区分则维持现状+记档）。另注意 DEPLOY.md §6.2 未披露此行为。

### L-1 relay: handleConn 设置的 REGISTER 10s 等待超时形同虚设
- `server.go:193` 设 AuthTimeout(10s)，随后 `session.go:59` readLoop 首轮立即以
  ReadTimeout(40s) 覆盖。因计划本就声明"不注册无害"，无实害，但代码意图失效，建议删除
  或改为真超时。（PLAN-005 §二.44"等 REGISTER（10s 超时）"）

### L-2 relay: Close() 不关闭桥接中的手机会话
- `server.go:140-150` 仅收集 macs/regs 两张表里的 Mac 会话；手机会话要等自身写失败或
  读超时才退出（最长 ~40s 残留）。进程退出场景影响小，建议一并收集 bridge 中的 phone。

### L-3 ratelimiter 条目只增不清（除成功清零）
- `ratelimit.go:97-101` 仅成功认证 delete；被锁后放弃攻击的 IP 条目永驻内存。
  个人中继量级可忽略，长期公网服务建议加定期清扫。

### L-4 Android: 切换激活设备/修改秘密后，运行中的服务不会生效
- `AudioStreamService.kt:102-117` 启动时固化 secretHex；MainActivity 芯片点击仅改
  DeviceStore（MainActivity.kt:135-139），不重启服务，状态条仍显示旧会话。同理
  免提/AEC 开关运行中修改不生效（startStreaming/startCapture 时各读一次）。
  建议：切换芯片时若服务在跑，提示或自动重启服务。

### L-5 Android reasonText 将 rate-limited 写死为"1 分钟后再试"
- RelayClient.kt:217；实际锁定递增至 30m（ratelimit.go:14-16）。文案误导。
